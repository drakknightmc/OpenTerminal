UI/UX plan · draft 1

A personal finance terminal, built as add-ons

OpenTerminal already has the two halves this needs: isolated provider modules on the server and a widget registry on the client. The plan keeps both, adds a section layer above the widget layer, and makes every agent write pass through one queue. Markets stays a workspace. Everything else is a fixed page, because fixed pages are denser, cheaper to render, and far cheaper to build.

5 · The add-on contract

Two kinds of add-on, deliberately different. A market widget is a view over a provider; a finance section owns data and therefore owns migrations, routes, and a review policy.

Widget add-on · markets only
registerWidget({
  type: "yieldcurve",
  title: "Yield curve",
  size: { w: 5, h: 7 },
  symbolAware: false,
  provider: "fred",
  view: YieldCurveWidget,
})
One file in web/components/widgets/, one line in the registry. No DB, no routes. This is the existing pattern in store/terminal.ts, lifted out of the switch statement into a map.
Section add-on · finance domains
registerSection({
  id: "subscriptions",
  label: "Subscriptions",
  group: "Flow",
  routes: subscriptionsRouter,
  migrations: ["001_recurring.sql"],
  pages: { index: List, detail: Detail },
  ingest: {
    accepts: ["expense.transaction"],
    review: "auto-above-0.9",
  },
  rollup: (ctx) => ctx.sum("recurring.monthly"),
})
The rollup is what lets Overview, Net worth and Statements stay generic: they render whatever sections register, in group order, with no knowledge of what a subscription is.
Ingest and the review queue

Every connector — Gmail MCP, the SMS relay, broker files, the EPFO scrape — writes a proposal row, never a ledger row. A proposal carries source, raw payload, parsed fields, target writes, and a confidence. The queue is the only place proposals become ledger rows, and the only place a bad parse can be corrected before it pollutes a rollup.

proposals(id, source, received_at, raw, parsed_json, target_section,
          writes_json, confidence, status, decided_at, decided_by)

Policy per section: always-review, auto-above-0.9, or auto. Auto-applied proposals still land in the queue as an applied row, so the audit log and the review list are the same table with a different filter. That is one screen doing all three jobs you asked for.
